# 分区画板协作协议

`partition_board` 让你把「怎么划片」这件拿不准的事交给人在画板上亲手画，
再由你补全剩下的、反复对齐，最后拿到一份你读得懂的规划继续干活。

这块画板**不属于 UI**。只要一件事的本体是「空间上划片 / 分块」，它都适用。

## 一、什么时候该调

该调：

- **界面分区**：页面/组件的区块怎么分、谁在谁里面、哪块自适应。人比你对产品直觉更准。
- **图像与版式构图**：海报、封面、信息图的画面切分与视觉重心。
- **文档/报告结构**：分节、每节占多大篇幅、哪些内容是附录。
- **数据或素材分段**：一批素材按什么维度分堆、边界在哪。
- **图示 / 示意图**：任何要在一个平面里划出区域的东西。
- **人主动要求画画**：「画个图给我看」「我在画板上标给你」——直接弹板，别用文字硬描述。
- **文字说不清就该画**：当你要描述的空间关系（哪里、多大、和谁相邻、谁盖住谁）一句话说不干净时，
  别硬写文字、也别拿 ASCII 图凑合 —— 用 `purpose: "other"` 弹板，请人画出来。
  这条是兜底判据，优先于上面所有分类。

### 抓自己：你正要做的动作 → 更该做的事

这张表是给「decision moment」用的。左列是你**已经在做/正准备做**的事（比分类名好认得多）：

| 你正准备…… | 更该做 |
| --- | --- |
| 写一段 3 行以上的版式/构图/层级描述 | 弹板，让他画。你那段文字他多半还得再问一轮 |
| 一次问用户 2 个以上空间问题（多宽？谁在上面？够不够？） | 弹板，一次问完 |
| 把布局画成 ASCII 方块图或缩进列表 | 弹板。ASCII 只能对齐形状，画不出「大概这一片」 |
| 猜「用户大概想要左边窄右边宽」 | 弹板。你猜得准，不是知道 |
| 拿着一个自己写的大纲继续往下做 | 如果这份大纲的**篇幅配比**由人定，先弹板；纯结构且人已认可就继续 |

### 别给自己开后门

写触发条件时特意没写「超过 N 行才调」这种阈值 —— 因为**阈值会被算**：
你一看「这个不到 3 行」就放过了，而那件事恰恰是「分几节、谁多谁少」这种
**看起来简单、实际只有用户知道**的结构问题。

所以：**上面分类里的事，不管看起来多小，都先弹板。**
反过来说，下面这些才是真的不该调：

不该调：

- 是非题、二选一、确认一个已经想清楚的方案 → 用 `ask_user_question`。
- 展示成品、仪表盘、表格、表单 → 用 `render_ui` 或 `dsh-ui` 围栏。
- **纯取证**（读文件、列目录、定位报错）→ 先取证，取证完发现边界本身有争议再弹板。
- 你自己已经能确定、且人能一眼看懂、他也没表达过疑问的简单分区 → 直接做，别浪费一次交互。

判据一句话：**需要一个人在平面上划出边界，或者你已经画了但拿不准，才弹板。**
拿不准时：**宁可多调一次。**

### 最省的一次调用（可以直接照抄）

```js
partition_board({
  purpose: "ui-layout",
  task: "首页版式",
  ask: "先把顶栏、主区、侧栏涂出来，命名看着改就行",
})
```

只有三个参数。`legend` 省了，画板会先摆 4 个待命颜色，用户改名字就能画；
`canvas`、`regions`、`targets`、`mode`（默认 `draw`）、`revision`（默认 1）全都可以省。

## 二、怎么调

```
partition_board({
  mode: "draw" | "review",
  purpose: "ui-layout" | "image-compose" | "doc-structure" | "data-segmentation" | "diagram" | "other",
  task: "这块画板为什么服务（显示在标题栏）",
  ask: "给用户的一句话操作指令",
  canvas: { aspect: "16:9", guide: "底图说明，会淡淡显示在画布上做参照" },
  legend: [{ id, color, name, meaning }],
  regions: [...],     // 你规划出的分区
  targets: [...],     // 你要重点处理的未标注/细小分区 id
  boardId, revision   // 迭代时必须是同一块板
})
```

硬规则：

1. **`legend` 是整块画板的语义底座。** 颜色本身没有意义，「红=主区、蓝=侧栏」才是。
   给每个色卡写清 `name`（短）和 `meaning`（判据，如「可滚动的正文，宽度自适应」）。
   颜色要有区分度，别给两个近似的红。
2. **`boardId` 与 `revision`。** 首轮省略 `boardId`（自动取本次调用 id），`revision` 省略即 1。
   **之后每一轮针对同一块板，必须把上一条 message 里的 `boardId` 传回来，并让 `revision` +1。**
   漏传 `boardId` 在 `review` 下会被工具**直接拒绝**（防止你把方案悄悄叠到一块新板上、用户看不到），
   在 `draw` 下则是新开一块空画板 —— 也就是说 `boardId` 丢了只会是这两种结果，都不是你想要的。
   `revision` 递增后，界面上更早的画板会自动折叠成一行摘要。
3. **`mode`。** 首轮用 `draw`（等用户画）；你出方案时用 `review`（画板把方案以虚线叠加，等确认或返工）。
4. **坐标全部归一化到 0..1**，左上为原点。`rect` 是 `[x, y, w, h]`；
   `poly` 是你自己规划的区域多边形；`stroke` 是折线笔触（带宽 `width`）。
   与画布像素无关，别写像素值。
5. **`softness`（0..1）是模糊边界**：边界要不要羽化、这块是不是「大概这一片」。
   做模糊分区时把 `softness` 调高（0.5 以上），并在 `meaning` 里说明是渐变过渡还是硬边界。

## 三、用户会回给你什么

每条消息都是 `[partition-board] {JSON}`。`kind` 只有三种：

### `plan-request` —— 用户画完了，要你补全

```json
{
  "kind": "plan-request",
  "boardId": "...", "revision": 2, "purpose": "ui-layout",
  "legend":  [{ "id": "a", "color": "#e5484d", "name": "主区", "meaning": "..." }],
  "regions": [{ "id": "r1", "colorId": "a", "kind": "rect", "rect": [0.1,0.1,0.3,0.2], "softness": 0.2 }],
  "grid":    { "cols": 32, "rows": 18, "cells": "000aaa00bb..." },
  "stats":   { "coverage": 0.62,
               "unlabeled": [{ "id":"u1","x":0.5,"y":0.6,"w":0.2,"h":0.3,"area":0.05 }],
               "tiny":      [{ "id":"t1","colorId":"a","x":0.02,"y":0.9,"w":0.04,"h":0.05,"area":0.003 }] },
  "targets": ["u1","t1"]
}
```

- `grid.cells` 是**行优先**的栅格矩阵，每格一个 base36 字符：`0` = 未标注，其余对应该轮 `legend`
  的**顺序索引 +1**（`1` = legend[0]，`a` = legend[10]）。用它推理空间关系最省事。
- `stats.unlabeled` 是没被任何分区盖住的连通区块；`stats.tiny` 是面积过小的碎块。
- 有的条目带 `small`（整块面积偏小的分区）、`feedback`（用户的返工意见）。
- **`note` 是用户自己写的文字说明**（画板右栏「边画边写」那段话）：他画的是什么、判断依据是什么。
  它和 `feedback` 是两条腿 —— `note` = 「我画的东西是什么」，`feedback` = 「你的方案要改什么」，
  别混。**收到 `note` 先读它再补全**：颜色和坐标表达不了的约束都在这儿
  （例如「左栏是筛选条件，主区要能并排看两张卡」）。

**你该做的**：读 `grid` 与 `stats`，理解用户已经画出的划分意图，
然后对未标注/细小区域给出方案 —— 用**同一个 boardId**、`revision` +1、`mode: "review"` 再调一次工具：
沿用原来的 `legend`（可加色卡，别改已有色卡的含义），把方案填进 `regions`（每块给 `colorId`、
几何、`softness`、以及 `note` 说明为什么这么分）。

### `rework` —— 用户对方案不满意

多带一个 `feedback`（要改什么）。同样 `revision` +1 重出方案：**只改 `feedback` 指向的部分**，
不要把用户已经画好的区域重画或改色。若反馈与你的判断冲突，按用户的来，并在 `note` 里记一句。

### `confirmed` —— 用户确认了最终规划

```json
{ "kind": "confirmed", "note": "用户边画边写的说明（有才带）",
  "plan": { "legend": [...], "regions": [...], "grid": {...}, "coverage": 0.98, "confirmedAt": "..." } }
```

画板到此结束（界面锁定只读）。**按 `purpose` 解读这份规划并推进项目**，不要再追问分区。

## 四、按 purpose 解读确认后的规划

| purpose | 这份规划是 | 你怎么推进 |
| --- | --- | --- |
| `ui-layout` / `ui-regions` | 界面区块与层级 | 每个色卡 = 一个区块职责。用 `rect` 的相对顺序还原嵌套与栅格；`softness` 高 = 这块与其他部分融合（如背景、渐变），不是独立卡片。先出结构，再出实现。 |
| `image-compose` | 画面构图 | 色卡 = 画面元素（主体/留白/背景/文字块）。用 `area` 判断视觉重心与留白比例，据此写构图或生成提示词。 |
| `doc-structure` | 文档分节与篇幅 | 色卡 = 章节角色；`rect.h` 的相对比例 = 篇幅配比；`grid` 里从上到下的位置 = 逻辑顺序。据此列大纲并分配篇幅。 |
| `data-segmentation` | 数据/素材分堆 | 色卡 = 分类标签与判据（`meaning` 就是分类规则）。用 `grid` 的位置信息对照原始数据的排布，把分类规则落成代码条件。 |
| `diagram` | 图示分区 | 色卡 = 泳道/层级/模块。先还原图的结构（节点与分组），再决定渲染方式。 |
| `other` | 自定用途 | 以 `legend[].meaning` 为准 —— 用户写的判据就是你这块板的语义契约。 |

**无论哪种用途**：`legend[].meaning` 优先于颜色本身；`softness` 高的边界要当作过渡而不是硬切；
`stats.coverage < 1` 的部分是用户没被覆盖的留白区，通常代表「这里没东西」而不是「这里漏了」。

## 五、收尾

- 规划确认后，把结论落成**你正在产出的东西**（代码结构、大纲、分类规则、提示词），
  而不是把 JSON 原样复述给用户。
- **要不要落盘**：默认它只存在于对话里。用户明确说要留存、要跨会话/跨浏览器还能找回来时，
  把 `plan` 写成 `<会话工作目录>/.dsh/boards/<boardId>.json`（一块板一个文件，同名覆盖）。
  这样同一块板在任何会话里都能按 `boardId` 找回来。**别自作主张建这个文件** ——
  用户选的是「只回传模型，由模型决定是否写文件」。
- 规划与你的既有方案冲突时，以用户画出来的为准，并把冲突点讲清楚，别默默改。

> 为什么画板不自己存到宿主：画板只在浏览器 `localStorage` 里记（按会话 + boardId），
> 换浏览器或清缓存就没了。**第三方客户端插件在 DSH 0.1.6 拿不到浏览器会话的鉴权器**
> —— `BrowserAuth` 是 connection 插件的私有字段而非 Cordis 服务，带 cookie 校验的
> `/api` 路由也归它独占；插件自己在 `webServer` 上开一条路由等于开一个没有 cookie 校验的口子。
> 所以跨浏览器留存的唯一安全路径就是上面那条：由你把确认后的 `plan` 写成文件。

## 六、反面清单

- ❌ 漏传 `boardId` / 忘记 `revision` +1 —— `review` 会被拒绝，`draw` 会让用户看到一块空板。
- ❌ 收到 `note` 却不读就补全 —— 那段话常常是用户唯一能说清「为什么这么分」的地方。
- ❌ 把 `softness` 当装饰。它表达的是「边界有多确定」，是语义，不是样式。
- ❌ 拿画板当问卷。它是空间问题，不是选项问题。
- ❌ 用户画了 3 块你却重画 10 块。先对齐用户已画的，再补他留下的空。
- ❌ 确认后还在问分区。确认即授权。
